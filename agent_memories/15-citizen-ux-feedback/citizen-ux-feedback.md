# LawCast 시민 접근성 UI/UX 피드백 (법률안 탐색 흐름 전수 분석)

분석 기준일: 2026-10-06 (동일일 2차 검증 패스 반영). 분석 대상: `frontend/` 전체 (라우트 6개 핵심 화면 + 주요 컴포넌트),
검증 방법: 코드 리뷰 + `DIFFCHAIN_UI_MOCK=1` 로컬 실행 화면 확인 — 홈, `/notices`, `/notices/[num]`,
`/notices/semantic-search`(결과/빈 결과/약한 관련도 reveal 흐름), `/webhook`, 토론 스레드 상세를
실제 브라우저에서 탐색하고, 주요 텍스트/배경 색상 쌍의 WCAG 대비율을 계산 스타일로 실측함.
범위: 화면·문구·흐름·접근성 관점의 실용적 피드백만 다루며, 법적/정책적 판단은 제외한다.

핵심 목표: **"일반 시민의 쉬운 법률안 접근"** — 비전문가(법률 지식 없음)가 (1) 나와 관련된
법률안을 찾고, (2) 무슨 내용인지 이해하고, (3) 할 수 있는 행동(열람/의견/공유/구독)을
발견하기까지의 여정을 기준으로 평가했다.

## 1. 목표 대비 현재 상태 요약

**한 줄 결론: 아카이브 "신뢰성"에는 최적화되어 있으나, 시민의 "이해와 행동" 경로는
2차적으로 방치되어 있다.** 현재 UI의 무게중심은 '증거 수집 플랫폼'(`routes/+page.svelte:158`
히어로 카피)에 맞춰져 있고, 시민 여정의 핵심인 (a) 기한 인지, (b) 참여(의견 제출) 동선,
(c) 비전문가 언어는 거의 설계되지 않았다.

잘 되어 있는 점 (목표에 부합하는 부분):

- **접근성 기반은 상위권**: 스킵 링크(`+layout.svelte`), 모바일 메뉴 포커스 트랩
  (`Header.svelte` `use:trapFocus`), `aria-label`/`aria-current`/`aria-live` 상시 사용,
  44px 터치 타깃, `prefers-reduced-motion` 대응(`app.css:1559,1586`), `data-testid` 후크.
- **URL 재현 설계**: 검색·필터·리비전 비교 상태가 URL에 반영되어 공유/새로고침이 재현됨
  (`notices/+page.svelte` `buildQueryLink`, `semantic-search/+page.svelte` `syncUrlQuery`).
- **책임 있는 AI 사용**: AI 요약을 항상 원문과 병치하고 오류 가능성을 명시
  (`AIBriefingCard.svelte`, 안내 배너). 요약 실패 시 대체 안내 제공.
- **의미 검색**: "세입자 보호" 같은 일상 언어 검색(`semantic-search/+page.svelte:283` 부연
  문구)은 목표와 가장 정확히 맞닿은 기능. 관련도 낮은 결과를 자동 노출하지 않고 사용자
  선택으로 reveal하는 설계도 훌륭함.
- **필터 피드백**: 적용된 필터 칩 + 개별 해제 링크(`notices/+page.svelte` `notices-active-filters`),
  빠른 기간 칩(최근 7일/30일/이번 달).
- **정직한 데이터 고지**: 발의 통계 페이지의 집계 기준 고지(`proposals/+page.svelte:725`),
  푸터의 "국회와 무관" 고지(`Footer.svelte`).

그러나 목표 관점에서 **결정적으로 빠진 3가지**:

1. **참여 동선 부재** — 입법예고의 본질인 "의견 제출"으로 가는 길이 UI 어디에도 없다.
2. **기한(D-day) 부재** — "지금 확인해야 하는 이유"가 화면에 표시되지 않는다.
3. **비전문가 언어 부재** — 전문용어(회부일·제안회기·Rev#·SHA256 지문 등)에 대한 어떤
   설명 장치도 없고, 히어로부터의 프레이밍이 '시민'이 아니라 '증거 수집'에 맞춰져 있다.

## 2. 발견된 문제점 (근거 포함)

### P1. 시민 참여(의견 제출) 동선이 통째로 없음 — **CRITICAL**

- **근거**: 상세 페이지의 액션 버튼군은 `토론 / 공유 / 국회 페이지 열기` 3개뿐
  (`routes/notices/[num]/+page.svelte:874` "국회 페이지 열기"). 전체 프론트엔드에서
  "의견 제출/의견등록/국민참여" 문구는 토론 댓글("의견 등록하기",
  `lib/components/discussions/ThreadDetailView.svelte:371`) 외에 존재하지 않음
  (grep 확인).
- **화면 검증(2차 패스)**: 상세 화면과 토론 스레드 상세(`/notices/[num]/discussions/[threadId]`)
  를 실제 렌더링에서 확인 — "의견 등록하기"는 스레드의 새 의견 작성 폼 버튼으로만 존재하고,
  "의견 제출"(국회 공식 참여) 문구는 두 화면 어디에도 없음. 두 화면 모두 "입법예고 기간"을
  참여 가능 기간으로 설명하는 문구 없음(본문 텍스트 검색 결과 0건). 스레드 작성 폼은
  닉네임/비밀번호/내용 입력 후 "의견 등록하기"로 제출되는 구조를 실제 타이핑+클릭으로 확인.
- **왜 장애인가**: 시민이 입법예고를 보는 궁극적 행동은 "의견 제출"이다. LawCast가
  수집하는 `noticePeriod`(입법예고 기간)가 곧 의견 제출 가능 기간인데, UI는 이 사실을
  한 줄도 말해주지 않는다. 시민은 "여기서 뭘 하면 되지?"에 답을 얻지 못하고 떠난다.
  "국회 페이지 열기"라는 중립적 CTA는 그 페이지에서 무엇을 해야 하는지를 알려주지 않는다.

### P2. 마감 기한(D-day) 정보가 화면에 없음 — **CRITICAL**

- **근거**: 목록 카드는 의안번호·상태 칩·제목·제안자 구분·소관위원회만 보여주고
  **날짜를 하나도 보여주지 않음** (`routes/notices/+page.svelte` 카드 블록, 화면 확인
  결과 동일). 상세의 "입법예고기간"은 raw 문자열 `"2026-06-14 ~ 2026-06-28"`로만 표시
  (`routes/notices/[num]/+page.svelte:257`). 상태는 `진행 중 / 입법예고 종료` 이진 칩뿐.
  "D-"/"마감" 표현은 프론트엔드 전체에 없음 (grep 확인).
- **화면 검증(2차 패스)**: 목록 카드 DOM에서 날짜 요소 0개, 상세의 "입법예고기간" 값이
  `2026-06-14 ~ 2026-06-28` 그대로 노출되는 것을 재확인.
- **왜 장애인가**: 시민이 법률안을 열어보는 가장 강한 동기는 "의견 낼 수 있는 기간이
  곧 끝난다"이다. 이 정보가 목록에서 안 보이면, 스캔 가능한 카드 목록은 사실상
  "제목만 나열된 게시판"이 된다. 진행 중/종료만으로는 긴급도를 알 수 없다.

### P3. 전문용어 무설명 + '증거 수집' 프레이밍 — **HIGH**

- **근거**:
  - 무설명 전문용어: "회부일", "제안회기"(`[num]/+page.svelte:249-260` contentFacts),
    "의안번호", "소관위원회", "Rev # / 리비전 / 비교 기준 / 비교 대상"
    (`lib/components/NoticeChangeTimeline.svelte`), "hash", "SHA256 지문", "무결성 검증",
    "HTTP 상태 코드", "원문 HTML 크기"(`[num]/+page.svelte` 아카이브 상세정보),
    "invalidated(무효화)", "보존 상태 전환(번호 변경)", "소스 미존재(보존)"
    (`notices/+page.svelte` 카드 칩). 툴팁/용어 설명/글로시어 어디에도 없음.
  - 홈 히어로: "국회 입법예고 **증거 수집 플랫폼**" (`routes/+page.svelte:158`), 상태 카드
    태그가 영문 `ARCHIVE / INTEGRITY / SYNC / REVIEW`.
- **왜 장애인가**: 비전문가는 "회부일"과 "제안회기"를 모른다. "증거 수집 플랫폼"이라는
  카피는 첫인상에서 "이 서비스는 나(시민)를 위한 것인가, 감사·기록 전문가를 위한 것인가"
  를 오인하게 만든다. 핵심 목표("쉬운 법률안 접근")와 첫 화면의 메시지가 어긋난다.

### P4. 검색 모델 3종의 복잡성과 불일치 — **HIGH**

- **근거**: (1) 홈 "통합 검색"은 `fullText=true`를 hidden으로 고정
  (`routes/+page.svelte:301`) — 항상 원문 포함 검색. (2) `/notices`에서는 동일 검색이
  "원문(제안이유) 포함 검색" 토글이고 꺼짐이 기본이며, 켤 때만 "속도가 느려질 수
  있습니다" title 툴팁(`notices/+page.svelte:648` 근처). (3) 의미 검색은 별도 페이지.
  세 모드의 차이를 설명하는 문구가 어디에도 없음. 빈 결과 화면은
  "검색 결과가 없습니다 / 다른 키워드로 다시 검색해보세요"뿐
  (`notices/+page.svelte:861-864`) — 의미 검색·필터 해제로의 연결 없음.
- **화면 검증(2차 패스)**: `/notices` 빈 결과 화면을 실제 검색으로 유발해 확인 — 안내 문구가
  위 두 줄뿐이고 빈 상태 박스 안에는 링크/버튼 0개. 다만 필터 폼의 "의미 검색" 버튼이
  현재 검색어를 그대로 넘겨주는(`?search=` 유지) 링크로는 존재 — 발견성 문제는 P5로 분리 유지.
  의미 검색 쪽 빈 결과(약한 관련도 0건)도 동일하게 "검색 결과가 없습니다 / 다른 표현으로
  다시 검색해보세요"만 표시되고 링크 0개임을 확인.
- **왜 장애인가**: 같은 검색창이 홈과 목록에서 서로 다른 규칙으로 동작하면 시민은
  "검색이 이상하다"고 느낀다(홈에서는 나오던 게 목록에서는 안 나옴). 검색 실패 시 다음
  행동을 제안하지 않는 빈 화면은 이탈 지점이다.

### P5. 의미 검색(핵심 시민 기능)의 발견성 부족 — **HIGH**

- **근거**: 의미 검색 진입점은 `/notices` 필터 폼 안의 작은 버튼 1개
  (`notices/+page.svelte` `semantic-search-entry`)뿐. 홈에는 언급 없음(빠른 키워드는
  전부 `buildQuickSearchHref` = 키워드 검색, `routes/+page.svelte:86`). 목록 빈 결과,
  상세 페이지 어디에서도 추천하지 않음.
- **화면 검증(2차 패스)**: 의미 검색 결과 화면 자체는 우수 — 일상 언어 설명 문구, 결과 칩
  (의안번호/유사도/섹션/위원회), "법률안 상세 보기" 링크, "전체 입법예고에서 키워드 검색하기"
  교차 링크가 모두 실제 렌더링에서 확인됨. 관련도 약한 결과의 reveal("관련도가 낮은 결과
  보기" → 배너+결과 노출 → "숨기기" → 빈 상태 복귀) 흐름을 클릭 사이클로 실측했고
  정상 동작함. 즉 기능 자체보다 '진입점 부재'가 문제라는 기존 결론 유지.
- **왜 장애인가**: "키워드를 몰라도 일상 언어로 찾을 수 있다"가 이 서비스의 시민 약속인데,
  그 기능을 찾으려면 이미 검색에 실패해 봐야 한다(그마저 빈 화면에는 링크가 없다).
  시민 친화 기능 1위가 히든 기능이 되어 있다.

### P6. 목록 카드의 정보 위계와 액션 가독성 — **MEDIUM**

- **근거**:
  - 날짜 부재(P2와 중복), 대신 "변경 기록 N건", "보존 상태 전환(번호 변경)" 같은 내부
    상태 칩이 상단을 점유.
  - 액션 3종이 아이콘 전용: "원문 조회"(텍스트), PDF/HWP 다운로드는 아이콘만
    (`aria-label`만 존재), 외부 링크도 아이콘만 (`notices/+page.svelte` 카드 우측).
  - "원문 조회" 버튼이 제목 링크와 동일 대상(`/notices/[num]?...`)을 가리켜 중복
    (`notices/+page.svelte:939`와 `notice-open-summary` 링크 동일 href).
  - 아이콘 의미 불일치: "제안자 구분"에 달력 아이콘(`faCalendar`), "소관위원회"에 종
    아이콘(`faBell`), 검색 빈 상태에도 종 아이콘.
- **왜 장애인가**: 시각 스캔 시 "이 법안이 언제까지인가" 대신 시스템 내부 상태가 먼저
  읽힌다. 라벨 없는 아이콘 버튼은 모바일/고령 사용자가 무엇을 하는 버튼인지 추측하게
  만든다.

### P7. 경고 배너 과잉이 원문 열람을 방해 — **MEDIUM**

- **근거**: 목록 상단에 AI 요약 안내 배너 상시 표시(`notices/+page.svelte:428`), 상세에는
  (보존 상태 배너 +) AI 안내 배너(`[num]/+page.svelte:896`)가 원문("제안이유 및 주요내용
  원문")보다 위에 위치. 동일 문구가 목록과 상세에 중복. 화면 확인 결과 상세 페이지에서
  실제 원문까지 스크롤 2~3번이 필요.
- **왜 장애인가**: "원문을 봐라"는 안내가 정작 원문을 화면 아래로 밀어낸다. 반복 노출은
  배너 실명화(무시)도 유발한다.

### P8. 원문 본문의 가독성 설계 부재 — **MEDIUM**

- **근거**: 제안이유 원문이 `text-sm leading-7 whitespace-pre-line` 단일 텍스트 블록
  (`[num]/+page.svelte` `notice-detail-proposal-reason`) — 고정 소자, 본문 폭 제한 없음,
  문단/소제목 구조 없음, 글자 크기 조절 없음.
- **왜 장애인가**: 법률 문장은 길고 복잡하다. 폰트 크기 조절조차 없으면 고령·저시력
  사용자가 원문(서비스가 가장 강조하는 "최종 기준")을 실제로 읽기 어렵다. AI 요약보다
  원문을 우위에 두겠다는 정책과 읽기 쉬운 원문 사이에 간극이 있다.

### P9. 필터 상태가 상세 왕복에서 유실됨 — **MEDIUM**

- **근거**: 목록→상세 링크는 `page, limit, search, startDate, endDate, sortOrder`만
  전달(`notices/+page.svelte:939` 근처 href)하고 `proposer, isDone, fullText, digest`는
  누락. 상세의 `backLink`도 동일 6개만 복원(`[num]/+page.svelte:276`). 제안자 필터로
  좁힌 결과 → 상세 열람 → "전체 입법예고" 복귀 시 제안자 필터가 사라짐. 제안자 링크로
  필터를 거는 경로가 목록에 있으면서(`notices/+page.svelte:961`) 그 상태가 유지되지 않는다.
- **왜 장애인가**: 시민이 어렵게 좁힌 결과가 뒤로 가기 한 번에 증발한다. 탐색을
  반복해야 하는 법률안 비교 작업에서 치명적이다.

### P10. 날짜 입력/표기의 혼재 — **LOW~MEDIUM**

- **근거**: 기간 필터가 `type="date"` 네이티브 피커인데 라벨이 `sr-only`이고
  `mm/dd/yyyy` 플레이스홀더가 그대로 노출(`notices/+page.svelte:592,603`, 화면 확인).
  날짜 표기도 화면마다 다름: 홈 "2026. 10. 6. 오후 12:53:21", 상세 chip "2026. 10. 1.
  오후 1:53:21", facts "2026-06-14". "오후 12:53"은 비표준(12:53 PM/오전 혼동).
- **왜 장애인가**: 한국 사용자에게 mm/dd/yyyy는 해석 오류를 만든다. 날짜 표기가 제각각이
  면 "언제 수집된 것"을 비교하기 어렵다.

### P11. 목록 페이지의 시각적 제목 부재 — **LOW**

- **근거**: `/notices`의 `<h1>`은 `sr-only`(`notices/+page.svelte:470`) — 시각 사용자는
  브레드크럼 작은 텍스트 다음 곧바로 경고 배너와 필터 폼을 만난다.
- **왜 장애인가**: 페이지 진입 시 "여기가 어디이고 무엇을 보는 화면인지"를 말해주는
  시각적 위계가 없다. 스크린리더 사용자에게는 h1이 제공되므로 접근성 자체는 유지되나,
  시각 사용자 경험에서 정보 위계가 약해진다.

### P12. md~lg 폭에서 내비게이션이 아이콘 전용 — **LOW**

- **근거**: 메뉴 라벨이 `hidden lg:inline`(`lib/components/Header.svelte:213`) —
  768px~1024px 구간에서는 아이콘만 표시. `title` 툴팁은 호버 전용.
- **왜 장애인가**: "발의 통계"(막대그래프), "변경 내역"(비교 아이콘) 등은 아이콘만으로
  의미 전달이 어렵다. 태블릿 사용자에게 내비게이션이 암호처럼 보인다.

### P13. 알림 설정의 높은 기술 장벽 — **MEDIUM**

- **근거**: `/webhook` 페이지가 Discord 웹훅 URL 입력
  (`lib/components/WebhookRegistrationForm.svelte:159-166`,
  placeholder `https://discord.com/api/webhooks/...`)을 최상단에 배치. 웹 푸시 동의는
  아래에 있음. 알림 단위는 "새 법률안 및 변경 감지" 전체 수신뿐이고 키워드/위원회 단위
  구독은 없음.
- **화면 검증(2차 패스)**: 실제 렌더링에서 확인 — DOM 순서는 "디스코드 웹훅 등록" 폼 →
  "브라우저 웹 푸시 알림" 섹션 순서로 P13의 배치 주장과 일치. 단 웹 푸시 섹션은 서버
  설정(`/api/push/public-key`)이 응답하지 않으면 통째로 hidden 처리되고
  (`WebPushConsentForm.svelte:360` `class:hidden={!isPushEnabledByServer}`), 모의 실행
  화면에서는 이 요청이 502로 실패해 시민에게 **Discord 웹훅 폼만** 노출됨. 즉 서버
  장애/미설정 상태에서는 "알림 설정" 첫 화면이 개발자 도구 하나만 남는 구조.
- **왜 장애인가**: Discord 웹훅 URL을 만드는 것은 일반 시민에게 사실상 불가능에 가깝다.
  "알림 설정"이라는 시민 친화적 메뉴명 뒤의 첫 화면이 개발자 도구이면, 시민은 알림
  기능이 자신에게 없는 기능이라고 판단한다.

### P14. 의미 검색 결과의 점수 언어화 부족 — **LOW**

- **근거**: 결과 칩에 "유사도 NN%"(`semantic-search/+page.svelte` `formatSimilarityPercent`)
  만 표시. 어떤 의미인지 설명 없음. (관련도 낮은 결과 reveal 흐름 자체는 우수.)
- **화면 검증(2차 패스)**: 실제 결과 칩의 표시 형식을 확인 — 명확 계층은 "유사도 59%",
  약한 계층은 "유사도 31%"로 노출되고, 어느 쪽에도 점수의 의미를 설명하는 툴팁/문구가
  없음. 이전 문서의 "유사도 87%"는 예시 표기였고 실측 형식은 "유사도 59%"(샘플 결과)임을
  확인해 정정함.
- **왜 장애인가**: "유사도 62%"가 좋은 건지 나쁜 건지 시민은 판단할 수 없다.

### P15. 색 대비 — WCAG AA 미충족 쌍 실측 확인 — **MEDIUM**

### P16. 장애 메시지가 원시 인프라 오류로 노출됨 — **MEDIUM**

- **근거(2차 패스 실측)**: 토론 새 의견 등록을 실제로 제출해 확인 — 백엔드 부재로
  `POST /api/discussions/threads/{id}/comments`가 502를 반환하면 화면의 빨간 오류 배너에
  "의견 등록 중 오류가 발생했습니다" 대신 **"Bad Gateway" 원문이 그대로 노출됨**.
  `discussionErrorMessage()`(`discussions/[threadId]/+page.svelte:175-177`)가
  rate-limit이 아닌 모든 오류에서 `error.message`를 그대로 통과시키기 때문.
  입력한 내용은 유지되어 재시도는 가능했음(이 부분은 긍정적).
- **왜 장애인가**: "Bad Gateway"는 시민에게 무엇을 어떻게 해야 하는지 알려주지 못하고,
  서비스 불안정 인상만 준다. 영문 인프라 오류가 한국어 UI에 그대로 섞여 노출된다.
- **구현됨(2026-10-06)**: `frontend/src/lib/utils/error-message.util.ts`의
  `toUserFacingErrorMessage()`으로 교체 — 한글 서버 메시지는 유지, 5xx/네트워크/검증 오류를
  구분해 한국어 행동 안내를 병기하고 원문은 콘솔 로그에만 남긴다. `discussionErrorMessage()`
  양쪽 구현(스레드 페이지·`NoticeDiscussions.svelte`)과 SSR `toLoadErrorPayload()`에 적용.
  e2e: `discussions.spec.ts`의 502/네트워크/토론 개설 실패 3건이 배너에 한국어 안내가
  노출되고 "Bad Gateway" 원문이 없음을 검증(개선안 13b).

## 4. 검증 방법 및 한계 (2차 패스 갱신)

**실제 화면 탐색으로 검증한 항목** (`DIFFCHAIN_UI_MOCK=1` 로컬 실행, 브라우저에서 실측):

- **의미 검색 결과 화면**: 결과 칩 형식("유사도 59%"/"유사도 31%", 섹션/위원회 칩),
  "법률안 상세 보기"·"전체 입법예고에서 키워드 검색하기" 링크 — P14 기록을 실측값으로 정정.
- **약한 관련도 reveal 흐름 전체 수명주기**: 빈 상태 → "관련도가 낮은 결과 보기" 클릭 →
  약한 결과+배너 노출 → "숨기기" 클릭 → 빈 상태 복귀까지 실제 클릭으로 확인(정상 동작).
- **빈 결과 화면 2종**: `/notices`("검색 결과가 없습니다/다른 키워드로 다시 검색해보세요"),
  의미 검색("검색 결과가 없습니다/다른 표현으로 다시 검색해보세요") — 양쪽 모두 빈 상태
  박스 안에 링크/버튼 0개 확인 → P4/P5 주장 확정.
- **웹훅 화면**: DOM 순서(Discord 웹훅 폼 → 웹 푸시 섹션) 확인. 단 `/api/push/public-key`
  502 시 웹 푸시 섹션이 hidden 되어 Discord 폼만 노출되는 상태를 실측 → P13에 반영.
- **토론 스레드 상세**: "의견 등록하기"가 새 의견 폼 버튼임을 확인(P1 확정). 실제 타이핑+
  제출 사이클을 돌려 (1) 서버 502 시 입력 내용 유지 + 오류 배너 노출을 확인하되
  (2) 배너에 "Bad Gateway" 원문이 노출되는 문제를 발견 → 신규 P16으로 기록.
- **주요 텍스트/배경 색상 쌍 12종 × 라이트·다크 2테마 대비율 실측**(계산 스타일 기반
  WCAG 상대 명도 대비, 배경은 조상 불투명 색 합성): 라이트 3건(`lc-text-dim` 2.37,
  `lc-text-muted` 4.39, 종료 카드 제목 4.39)·다크 1건(`lc-button-primary` 2.99)이
  AA 본문 기준(4.5:1) 미충족 — P15에 수치와 함께 기록.

**여전히 미검증인 항목** (한계로 유지):

- 실제 스크린리더(NVDA/VoiceOver) 체감, 모바일 실기기 터치 경험, 키보드 전용 탐색의
  체감 흐름은 미검증.
- 대비 측정은 `/notices` 화면의 대표 12쌍에 한정 — 전체 페이지/모든 칩 변종·상태
  (hover/focus/disabled)의 전수 대비 검증은 미실시. 측정 스크립트는 계산 스타일 기반이라
  color-mix/그라디언트 배경은 근사치일 수 있음.
- 모의 실행의 쓰기 경로(댓글 등록 POST 등)는 mock이 미커버해 502로 떨어지며, 따라서
  **성공 시나리오의 서버 저장→재조회 수명주기는 미검증**(UI의 실패 처리만 검증).
- 백엔드 스키마(`noticePeriod` 파싱 가능성, 키워드 알림 구독 API) 일부 제안은 백엔드
  확장이 전제되며, 해당 항목은 P3로 분류했다.
