- **NSM zero-row list scans are a latched failure state (2026-10-14)**: a completed NSM list scan with zero rows is recorded as a failed observation in the cache key `crawling:nsmListScanHealth` (no expiry) and, after `CRAWLING_NSM_LIST_SCAN_DEGRADED_THRESHOLD` consecutive zero-row cycles (default 3), escalates to an ERROR alert and `crawlers.nsmPendingCrawler.status === 'degraded'` on `/api/stats`. Things to keep in mind: (1) the streak counts **cycles**, not scans — `NSM_LIST_SCAN_DEDUPE_WINDOW_MS` (5 min) folds the cron pass and the archive-sync pending phase of one cycle together, so a test that wants a growing streak must advance the clock (`jest.useFakeTimers()` + `jest.setSystemTime`) rather than calling `handlePendingCron()` three times in a row; (2) repeat alerts are rate-limited by `CRAWLING_NSM_LIST_SCAN_ALERT_REPEAT_HOURS`, so "no second alert" is expected, not a bug; (3) `reportNsmListScanOutcome` must stay non-throwing — a cache failure degrades to the plain zero-row warning so a bookkeeping outage never fails a crawl (specs cover both sides); (4) the reporter needs `cacheService.getObject/setObject` on the crawl deps, so CacheService doubles in scheduler/archive-sync specs must provide both (the existing objectStore-backed mocks already do); (5) recovery clears the streak and reports how many scans were empty — do not "fix" `degraded` by clearing the record in the API, it is the latch the status page reads.

- **NSM list-absence tracking is column-based, not set-difference-based (2026-10-14)**: source-deletion candidates come from `notice_archives.nsm_last_seen_in_list_at` (last completed list scan that returned the row) and are throttled by `nsm_list_absence_probed_at` + `ARCHIVE_SYNC_NSM_LIST_ABSENCE_REPROBE_COOLDOWN_HOURS` (default 168). Invariants: (1) `markSourceDeletedByMissingNsmNums` stamps the whole seen-set BEFORE selecting candidates, so rows returned by the current scan can never be candidates; never compare the archive against the seen-set in JS — that is the ~10k-per-cycle probe storm (`agent_memories/32-nsm-ua-block-and-probe-storm/`). (2) Rows never seen in a list (`NULL`) are only filler behind newly disappeared rows (oldest disappearance first) and drain at `ARCHIVE_SYNC_NSM_MISSING_PROBE_MAX_CANDIDATES` per pass. (3) Every non-`deleted` probe outcome (including `blocked`/`error`) stamps the cooldown, and sighting stamps happen even while `CRAWLING_NSM_DELETION_DETECTION_ENABLED=false`, so re-enabling detection resumes with "disappeared while it was off". (4) Both new columns are updatable through the archive immutability trigger (only tracking columns change); the trigger itself was not modified. (5) These are two grouped `repository.find` calls (`LessThan(scannedAt)` vs `IsNull()`) whose `take` carries the cap — hand-rolled repository mocks must answer per group and honour `take`; the real-SQLite spec is `notice-archive-nsm-list-absence.spec.ts`. The NSM **detail** probe path (`getActiveNsmBillsForProbe`) still re-samples its pool every cycle — extend the same cooldown column rather than reintroducing randomness if it needs throttling.

- **NSM deletion probes are classified, not boolean (2026-10-14)**: `CrawlingCoreService.probeNsmDeletedBillOutcome()` returns `NsmDeletionProbeResult` with `outcome: 'deleted' | 'alive' | 'blocked' | 'error' | 'disabled'` — `blocked` means the response was the portal's own error page (`isNsmPortalErrorPageHtml`: `errorWrap` class or `요청페이지가 없습니다`) or the Waitingroom, i.e. **unreadable, never "alive"**. `probeNsmDeletedBillAlert()` still exists but is a thin wrapper returning the message only for `deleted`. `NoticeArchiveService.markSourceDeletedByMissingNsmNums(set, confirmDeletion, options?)` now expects that outcome string from `confirmDeletion` (not a boolean), caps each pass at `options.maxCandidates` (default `ARCHIVE_SYNC_NSM_MISSING_PROBE_MAX_CANDIDATES=50`, random sample so the pool is covered across passes) and aborts the pass after `options.unusableAbortThreshold` (default 5) consecutive unusable probes with zero readable pages. Any new caller that returns a boolean or treats `blocked` as alive re-opens the silent block documented in `agent_memories/32-nsm-ua-block-and-probe-storm/nsm-portal-block-and-probe-storm.md`.

- **NSM list source is switchable (pal-crawl 2.3.0, 2026-10-14)**: `CRAWLING_NSM_SOURCE=likms` makes `CrawlingCoreService.createNsmClient()` return pal-crawl's `LikmsNsmAdapter` (국회 의안정보시스템 `계류의안`) instead of `NsmLmSts`; both satisfy the same `INsmListCrawler`/`INsmDetailCrawler` ports, so `getAllNsmPages`/`getAllNsmPendingPages`/`getNsmDetail` call sites are source-agnostic. Three things to remember: (1) `searchPending`/`getAllPendingPages` are deliberately **not** in `INsmListCrawler` (likms has no server-side pending filter and must scan), so type the client with a local port type; (2) the pending status word differs (`발의` on NSM vs `접수` on likms) — use `CrawlingCoreService.isPendingProgressStatus`, never a literal; (3) the likms `계류의안` list also contains **non-bill rows with non-numeric ids** (e.g. 인사청문요청안 with `billNo` `ZZ22142`, observed live), and the pipeline keys everything on the numeric `의안번호`, so both `collectPageItems` implementations must drop them via `CrawlingCoreService.isCrawlableNsmBill` before `nsmBillToCachedNotice` (otherwise `num=NaN` reaches the archive). Also: `hydrateProposalReason` must NOT be passed to the adapter's bulk list scans (2 extra requests per bill). Details: `agent_memories/31-likms-nsm-adapter-integration/likms-nsm-adapter-integration.md`.

- **Change-notification exclusion implemented (2026-10-09, plan: `agent_memories/19-change-notification-exclusion/plan.md`)**: `ChangeTrackingService.dispatchChangeNotification` now skips `NOTIFICATION_EXCLUDED_SOURCES` (`archive:updateNsmHtmlAndDetail`, `archive:likmsProposalReason` — internal backfill/repair runs) after the existing suppression/created/`bootstrap:` gates. **Invariant: exclusion lives ONLY in the dispatch gate** — the diffchain event append, `resetSummaryStateForProposalReasonChange`, chain audit and `/api/notices/changes` timeline must keep recording backfill events; never "fix" noise by skipping the append. Consequence for tests: specs that used `ARCHIVE_UPDATE_NSM_HTML_AND_DETAIL` merely as a convenient UPDATED payload source (e.g. the NSM->PAL flag and auto-flush tests in `change-tracking.service.spec.ts`) must use `ARCHIVE_UPSERT` instead, otherwise the new gate drops the payload. Phase 2: `reconcileIsDonePhase` (`archive-sync-phase-executors.ts`) is now fetch-all -> dry-count (`NoticeArchiveService.countNotDoneByNoticeNums`) -> mark, and wraps marking in `begin/endChangeNotificationSuppression` when pending flips exceed `IS_DONE_SYNC_NOTIFY_LIMIT` (500; measured normal daily max 283 vs 17,224 in one run on 2026-08-10); events are still written, only notifications are suppressed. Hand-crafted `NoticeArchiveService` provider mocks in `fault-isolation.spec.ts` need the new `countNotDoneByNoticeNums` method or the phase crashes (same mock-sync pitfall as `CacheService`). Success status of `getIsDoneSyncStatus()` is `'idle'`, not `'ok'`.



- Crawler User-Agent rotation relies on a pal-crawl implementation contract: `HttpClient.makeRequest` builds each request's headers as `{ 'User-Agent': config.userAgent, ...config.customHeaders, ...extraHeaders }`, and an object spread reads own keys in insertion order and invokes accessors. `createCrawlerClientHeaders()` (`src/utils/browser-request-headers.util.ts`) exploits that to rotate the identity per request through `customHeaders` (with `User-Agent` defined first, so the client hints describe the same identity). Keep `browser-request-headers.util.spec.ts` in the loop: it stubs `https.request` and drives the real `NsmLmSts.search()`, so a pal-crawl release that reorders the spread or stops evaluating accessors fails the suite instead of silently pinning one User-Agent.
- Browser identities are family-coherent by construction: Chromium sends `sec-ch-ua*`, Chromium and Firefox send `Sec-Fetch-*`, Safari sends neither, and the version in `sec-ch-ua` must equal the one in the User-Agent. Never add a header from one family on top of another family's User-Agent, and never set `Accept-Encoding` on the pal-crawl HTTP path (`HttpClient` does not decompress, so the body would arrive as raw gzip).

- **proposalReason retry candidates advance by attempt history (2026-10-15)**: `getProposalReasonRetryCandidates` pages by `proposal_reason_retry_count ASC, proposal_reason_retried_at ASC, noticeNum ASC` (columns added in `202610150001-add-proposal-reason-retry-tracking.migration.ts`), and the drain stamps what it attempted through `CrawlingSchedulerProposalRetry.recordAttempts` → `NoticeArchiveService.recordProposalReasonAttempts`. Invariants: (1) **any new path that seeds the retry queue must stamp its attempts**, otherwise the page keeps returning the same head — the production wedge was 20 unrecoverable non-bill rows (`사직의건`/`결의안`, `contentId IS NULL`) re-seeded every 15 minutes while the 180 recoverable bills behind them were never reached (`agent_memories/39-likms-reason-backfill-throughput/`); (2) the recorder is optional in the compat cast used by the retry support (`recordProposalReasonAttempts?`), so a hand-rolled `noticeArchiveService` double without it silently disables rotation — the doubles in `crawling-scheduler-proposal-retry.spec.ts` now expose it, and a throwing recorder must NOT fail the drain (covered by a dedicated case); (3) both columns are outside the immutability trigger's unchanged-column list (like the list-sighting stamps), so the stamp UPDATE needs no trigger migration — `archive-immutability-trigger.spec.ts` pins allowed-vs-bundled-with-an-immutable-column behaviour; (4) in queue doubles, `deleteKey` must clear the stored copy because `setQueue([])` deletes the key instead of storing `[]` — otherwise `getQueueLength()` keeps reporting the pre-drain rows; (5) no index was added for the new sort keys: a production-shaped bench (21,494 archives / 925 candidates / 745 already stamped) measured 29.700 ms vs 29.785 ms median for the old vs new ordering, i.e. the NOT EXISTS subqueries dominate and the extra sort key is below measurement noise.

- **Digest aggregation spans producer batches (2026-10-23)**: `NotificationBatchService.processNotificationBatch` and `processChangeNotificationBatch` now enqueue into separate `NotificationDigestBuffer` instances instead of immediately starting delivery. Each buffer waits for 30 seconds without a new non-empty batch, capped at 120 seconds from the first enqueue (`backend/src/modules/notification/notification-digest-buffer.ts:5-6,25-42`). This closes fragmentation from the upstream 100ms change timer (`change-tracking.service.ts:1036-1048`), collection-end flushes, and independent new-notice producer calls. Discord's eight-item preview (`notification.service.ts`, `createNotificationDigestEmbed`) is a display limit, not a batch split. Existing change categories still send separately (ordinary changes, period ended, source deleted, NSM-to-PAL), and new notices stay separate from changes. Calls merged into one window share the first batch ID and execution options; direct `execute*Batch` calls still send immediately. **Shutdown order matters**: drain `flushPendingNotifications()` before `BatchProcessingService.gracefulShutdown()` rejects new jobs (`backend/src/main.ts:173-177`); the module destroy hook also drains pending and in-flight deliveries. Buffers are in memory, so forced process termination can discard their contents. Regression tests in `notification-batch.service.spec.ts` use fake time to verify 8+9+8 arrivals become one 25-event digest on both channels, the two-minute cap, independent windows, empty calls, and pending/in-flight shutdown; the batch e2e spec explicitly drains the buffer rather than sleeping.
