# /notices 검색 UI 페르소나 사용성 실측 및 개선

`/notices`(전체 입법예고) 검색 UI가 **전문 법률 지식이 없는 일반 시민부터 법조인까지**
모두에게 높은 활용도를 주는지 실측하고, 실측 근거가 있는 항목만 개선한 기록.
대상은 세션 28(Phase 2)에서 배선한 검색 방식 컨트롤·관련도 칩·폴백/약한 계층 UI 전체.

**Status: 실측 완료 · 개선 5건 + 대칭 회복 1건 + 후속 라운드 5건 구현 완료 (2026-10-13).**
1차는 `DIFFCHAIN_UI_MOCK=1` 실측(§1~§4), 2차는 실 백엔드/엔진까지 붙여 한계를 재검토하고
남은 항목을 처리했다(§5~§7).

---

## 1. 실측 방법

추측을 배제하기 위해 실제 렌더 결과를 측정했다. 백엔드 없이 UI 계층만 보는 것이
목적이므로 mock 모드로 고정했다.

```bash
cd frontend && PUBLIC_SEMANTIC_SEARCH_ENABLED=1 DIFFCHAIN_UI_MOCK=1 \
  npm run dev -- --port 5199 --strictPort
```

| 축 | 방법 |
| -- | ---- |
| 상태 커버리지 | SSR HTML 프로브: 콜드 스타트 / 키워드 결과 / 의미 결과 / 0건(키워드) / 0건(의미) / 약한 계층 / 엔진 폴백 / 숫자 질의 |
| 브라우저 실측 | 1440x900, 390x844에서 `innerText`·`getBoundingClientRect`·`scrollWidth` 수집, 스크린샷 육안 확인 |
| 인터랙션 | 예시 칩 클릭 → 의미 검색 실행, 모드 전환, 빈 상태 회복 버튼 href, `title` 툴팁 존재 |
| 접근성 | 입력/셀렉트 `label` 연결, `aria-current`/`aria-checked`, 탭 영역 높이 |

페르소나는 세 축으로 나눴다. **시민**(법률 용어 없이 일상어로 검색), **법조인**(누락 없는
전집 확인이 필요), **중간**(기자·보좌진: 빠른 훑기 + 정확한 재검색).

## 3. 구현한 개선

카피는 `src/lib/utils/semantic-search.ts`에 단일 소유로 두고(컨트롤 힌트 = 옵션
툴팁 = 동일 문자열), 플래그가 꺼진 보드는 여전히 바이트 단위로 동일하다.

| # | 변경 | 위치 |
| - | ---- | ---- |
| A | 모드별 1줄 설명 `BOARD_SEARCH_MODE_HINTS` — 선택된 모드 아래에 상시 노출 + 각 옵션 `title` | `utils/semantic-search.ts`, `+page.svelte` (`notices-search-mode-hint`) |
| B | `appliedMode === 'semantic' && 결과 있음`일 때 결과 요약 아래에 범위 고지: "관련도순 상위 결과를 보여드려요. 전체 결과는 [키워드 검색]에서 확인할 수 있어요." 링크는 쿼리를 유지한 채 keyword로 전환 | `+page.svelte` (`notices-semantic-scope-note`, `notices-semantic-scope-keyword`) |
| C | 빈 상태에 회복 동선: (a) 의미 미적용 시 `의미 검색으로 다시 찾기`(auto), (b) 기간/상태/원문 등 **키워드 외 필터**가 활성이면 `기간·상태 조건 지우기` | `+page.svelte` (`notices-empty-try-semantic`, `notices-empty-reset-filters`), 신규 `hasNonKeywordFilters` |
| D | 칩 설명 `BOARD_RELEVANCE_HINTS`(score/section/excerpt) → 카드·약한 계층 칩과 발췌문 전체에 `title` | `utils/semantic-search.ts`, `+page.svelte` |
| E | 콜드 스타트(쿼리 없음)에서 `예시 검색어` 3개 노출. 기존 큐레이션 풀(`SEMANTIC_EXAMPLE_QUERIES`) 재사용, 각 칩은 `?search=<예시>&searchMode=auto` | `utils/semantic-search.ts`(기존), `+page.server.ts`(`pickExampleQueries`), `+page.svelte` (`notices-example-queries`) |
| F | 의미 모드 0건일 때 `키워드 검색으로 다시 찾기` 노출 → B의 고지와 대칭 | `+page.svelte` (`notices-empty-try-keyword`) |

**설계 판단**

- **예시는 로더에서 뽑는다.** 클라이언트에서 뽑으면 첫 페인트 직후 칩이 교체되어 깜빡인다
  (세션 08 프론트 노트와 동일 원칙). 서버 로드 결과를 SSR HTML과 하이드레이션이 공유한다.
- **B는 결과가 있을 때만.** 0건인데 "상위 결과를 보여드려요"라고 말하면 거짓이고,
  그 상황은 C/F가 이미 회복 동선을 제공한다.
- **B는 플래그로 막지 않는다.** 서버가 실제로 의미 결과를 반환했을 때만 뜨므로(프론트는
  플래그가 꺼지면 `searchMode`를 보내지 않는다) 정상 동선에선 발생하지 않고, URL을 직접
  조작한 경우에도 정확한 고지가 되는 편이 낫다.
- **A의 힌트는 선택된 모드 1개만** 노출한다. 3개를 동시에 쓰면 검색 패널이 설명문으로
  가득 차 정작 입력란이 묻힌다.

### 5.1 모드별 건수 의미 불일치 (발견 → 수정)

실 백엔드 계약에서 **의미 모드의 `stats.totalArchiveCount`는 전체 아카이브(21,188)이고,
키워드 모드는 매칭 건수**다. 보드는 이 값을 SEO 설명·요약줄에 그대로 썼기 때문에
`search=국민`(실제 39건)이 문서 제목에서 **21,188건**으로 광고됐다. 실측으로 확인하고
결과 건수(=`total`)를 쓰도록 고쳤다(제목이 `전체 39건`).

같은 불일치가 mock에도 그대로 옮겨져 있다(`getMockArchiveNoticesResponse`가 의미 경로에서
`totalArchiveCount`를 전체 mock 아카이브로 바꿔치기) — 테스트가 실 계약을 속이지 않도록 유지.

### 5.2 전집 대조: 온디맨드 키워드 건수 (수정)

법조인이 "이 39건이 전부인가"를 바로 볼 수 있게, 범위 고지에서 **같은 조건의 키워드 건수를
버튼으로 요청**해 받는다(`notices-semantic-scope-count` → `-count-result`). 실제 응답으로
**의미 39건 vs 키워드 509건**이 한 화면에 나온다.

- 검색마다 자동으로 부르지 않는다(의미 검색 한 번에 이미 1초 가까이 걸린다). 1회 요청, 사용자가
  누를 때만.
- 저장된 건수는 `filterSignature`(쿼리·제안자·기간·정렬·상태·원문)에 묶어 두어, 검색어를 바꾸면
  즉시 버튼 상태로 돌아간다(이전 필터의 숫자를 새 검색에 인용하는 사고 방지).
- 이 호출은 **브라우저가** `/api/notices/archive`를 때린다. mock 모드의 `handleFetch`는 SSR만
  가로채므로 프록시 라우트(`routes/api/[...path]/+server.ts`)에 archive 분기를 추가했다 — 없으면
  mock 모드에서 백엔드 부재 502가 나 테스트 경로가 사라진다.

### 5.3 예시 검색어 결정화 → 되돌림 (2026-10-13)

이 라운드에서 `pickExampleQueries()`를 **KST 날짜 기준 결정적**(`dayIndex`, 보폭 7 — 풀 18개와
서로소라 충돌 불가)으로 바꿨으나, 같은 날 방문자 전원이 동일한 3개를 보게 되어 칩의 목적
(이 입력창이 받는 질문의 폭을 보여주기)이 사라졌다는 판단으로 **원래의 요청별 랜덤 추출로
되돌렸다**(오너 결정). 측정했던 이득(같은 URL 2회 로드의 SSR HTML 바이트 동일)은 캐시·로그
관점의 이점이었을 뿐 사용자에게 보이는 문제가 아니었고, 랜덤이어도 SSR payload가 칩을 실어
보내므로 hydration 후 스왑은 없다(`semantic-search.spec.ts`의 `captureSsrChips`가 고정).

**되돌리지 말 것**: 날짜·요청 단위 결정화를 다시 넣지 않는다. 회귀를 막는 테스트는
`e2e/semantic-search-board.spec.ts`의 칩 테스트로, 이제 **서로 다른 3개 + 풀 소속**만 검증한다
(로드 간 동일성을 기대하지 않는다 — 독립 추출 2회가 같은 3-집합일 확률이 1/C(18,3)≈0.12%라
"달라짐"을 단언하면 깜빡이는 테스트가 된다).

**후속(같은 날): 랜덤을 유지한 채 캐시 위험을 닫았다.** 결정화의 원래 명분이었던 "같은 URL이 매번
다른 HTML" 문제는, SvelteKit이 동적 페이지에 `Cache-Control`을 내보내지 않아 **공유 캐시가 한
방문자의 추출을 모두에게 재생**할 수 있다는 진짜 위험으로 다시 정리됐다(그러면 칩이 다시 고정돼
보인다). 두 라우트(`/notices`, `/notices/semantic-search`)의 로더가
`lib/server/ssr-cache-policy.ts`의 `PER_REQUEST_HTML_CACHE_CONTROL`(`private, no-cache`)을
`setHeaders`로 내보내도록 했다. 검증: 두 스펙에 헤더 단언 추가 + 프로덕션 빌드(`build:node`)에서도
미니파이 훅을 거쳐 헤더가 살아남는지 확인. 결정화 대신 이 방향을 택한 이유: 사용자에게 보여줄 것을
바꾸지 않으면서 캐시가 잘못된 값을 고정하는 경로만 차단한다.

### 5.4 약한 계층 폭주 (신규 발견 → 수정)

**측정**: 실 엔진에서 `search=달빛조각사`(아무 관련 없는 소설 제목)는 명확 결과 0건,
**약한 계층 100건**을 반환했다. 점수는 0.334~0.393 한 줄 대역 — 사실상 "모두 똑같이
무관함"인데, 보드와 전용 페이지는 이를 **상한 없이** 렌더링해 100장 카드를 쏟았다.

백엔드 상한은 `semanticSearch.hybridMaxNotices`(기본 100)라 `100건`은 **잘린 숫자**일 수도 있다.
따라서 "몇 건인지"만 말하고 전부 그리면 거짓·노이즈 둘 다 된다.

**수정**: 약한 계층을 `WEAK_RESULT_PAGE_SIZE`(10) 배치로 페이징한다. 문구·배치 상수는
`utils/semantic-search.ts` 단일 소유(`describeWeakReveal`/`describeWeakProgress`)라 보드와 전용
페이지가 어긋나지 않는다.

| 상태 | 표시 |
| ---- | ---- |
| 공개 전(12건) | `관련도가 낮은 결과가 12건 있어요. 관련도가 높은 10건부터 보여드려요.` |
| 공개 후 | 카드 10장 + 배너 `12건 중 10건 표시 중` + `관련도가 낮은 결과 더 보기 (10/12)` |
| 더 보기 후 | 카드 12장, 더 보기·진행률 사라짐 |
| 숨기기 → 재공개 | 다시 10장(배치 초기화) |
| 전용 페이지 헤드라인 | 배치가 아니라 밴드 전체를 말한다(`… 검색 결과 12건`) |

### 6.1 신규 e2e: 보드 의미 UI에 자동 검증을 붙임

1차 라운드의 보드 기능(모드 힌트·예시 칩·범위 고지·온디맨드 건수·약한 계층)은 **수동
브라우저 측정으로만** 검증되어 있었다(`searchMode`를 쓰는 스펙 파일이 0개).
`e2e/semantic-search-board.spec.ts` 6개 테스트로 고정했다.

- 콜드 스타트: 모드 3개 + 각 옵션 `title` + 힌트 + 예시 3개 + 리로드 후 예시 유지
- 예시 칩 클릭 → `?search=<예시>&searchMode=auto`, 입력란 프리필, 예시행 소멸
- 의미 결과: 범위 고지·키워드 링크 href·관련도 `title`, 건수 버튼이 실제로 `limit=1` 조회를
  발생시키는지 요청 단위로 확인
- 검색어 변경 후 건수가 stale로 남지 않는지
- 키워드 모드: 범위 고지·관련도 칩 0개
- 약한 계층: 제안 문구 → 10장 → 더 보기 12장 → 숨기기/재공개 10장

**주의(함정)**: 보드 컨트롤은 하이드레이션 전 클릭이 무음 no-op이라 단발 `click()`은 간헐
실패한다. `clickUntil()`(`expect(...).toPass()`)로 클릭과 효과를 함께 재시도한다.

### 6.2 실 엔진에서 확인한 계약 (보드 관점)

## 7. 남은 관찰

- **모드 칩 터치 영역 24px** — 전역 칩 관례와 동일. 전역 상향은 별도 판단.
- **두 모드 결과를 나란히 보는 대조 뷰** — 지금은 건수만 온디맨드로 본다. 좌우 비교는 별도 기능.
- **`weakResults` 100건 상한** — 백엔드 `hybridMaxNotices`가 상한이라 "100건"이 잘린 값일 수
  있다. 프론트는 payload 길이만 말하고("12건 중") 상한을 단정하지 않는다. 정확한 총계가
  필요하면 엔진이 전체 카운트를 내려줘야 한다.
- **`proposalReason` 등 본문 발췌 품질** — 약한 계층 발췌는 여전히 원문 일부라 무관한 쿼리에서는
  노이즈다(페이징으로 노출량만 줄였다).
